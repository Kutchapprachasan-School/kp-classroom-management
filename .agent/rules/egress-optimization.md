# ZERO-EGRESS & DATABASE WORKLOAD OPTIMIZATION RULES
# (กฎเหล็ก 7 เสาหลักลด Egress สูงสุด และประหยัด Compute Hours สำหรับ Neon Serverless)

ความเป็นมา:
ในการพัฒนาระบบที่มีขนาดใหญ่แต่ทำงานบน Cloud Database แพลนประหยัดหรือฟรี (เช่น Neon Serverless PostgreSQL)
ปริมาณ Egress (Data Transfer) และ Compute Usage Hours เป็นทรัพยากรที่มีโควตาจำกัด (เช่น Egress 5 GB/เดือน, Compute ~100-190 CU-hours/เดือน)
การเขียนโค้ดที่ขาดความระมัดระวังเพียงจุดเดียว (เช่น SELECT * ก้อน JSONB หรือ Polling ถี่ๆ) สามารถผลาญโควตาทั้งเดือนหมดลงได้ภายในไม่กี่วัน

AI Assistant และ Developer ทุกคนที่พัฒนาโปรเจกต์นี้ต้องปฏิบัติตาม 7 เสาหลักนี้อย่างเคร่งครัด:

==================================================
1. 🎯 STRICT FIELD WHITELISTING (ห้าม SELECT * โดยเด็ดขาด)
==================================================
- **ห้ามเด็ดขาด**: ห้ามเขียน `SELECT *` หรือ `prisma.<model>.findMany()` โดยไม่ใส่ `select:`
- **กฎการคัดเลือกคอลัมน์**:
  - ต้องระบุเฉพาะคอลัมน์ที่ UI หน้าจอนั้นต้องใช้จริงเท่านั้น เช่น `id, name, username, email, role, position`
  - คอลัมน์ขนาดใหญ่หรือ Binary/JSONB เช่น `faceDescriptor`, `signatureUrl`, `image`, `data` ต้องแยกคิวรี่เฉพาะหน้ารายละเอียดหรือเมื่อจำเป็นต้องประมวลผลจริงเท่านั้น
  - ห้ามดึงก้อนข้อมูลส่วนบุคคลหรือข้อมูลสแกนใบหน้าของทุกคนมารวมในตารางรายชื่อ

==================================================
2. ⏱️ TIMESTAMP & FINGERPRINT GUARD (เช็ค UPDATED_AT ก่อนโหลดเนื้อหา)
==================================================
- **ห้ามดาวน์โหลด Data Body ก้อนใหญ่ทันทีที่เปิดหน้าเว็บ**:
  - **Step 1 (Check)**: คิวรี่เฉพาะคอลัมน์ `updated_at` หรือ Fingerprint สรุป (เช่น `count(*)`, `max(updated_at)`)
  - **Step 2 (Compare)**: นำ Timestamp ที่ได้มาเทียบกับค่าที่บันทึกไว้ใน `localStorage` / In-Memory Cache
  - **Step 3 (Fetch)**: สั่งดาวน์โหลดข้อมูลเต็มรูปแบบก็ต่อเมื่อข้อมูลบน Cloud ใหม่กว่าบนเครื่อง Client เท่านั้น
  - หาก Timestamp ตรงกัน ให้ใช้ข้อมูลจาก Cache ท้องถิ่นทันที (Bandwidth consumed = 0 bytes)

==================================================
3. ✂️ MINIMAL MUTATION RETURN (ห้ามใช้ RETURNING *)
==================================================
- เมื่อทำคำสั่ง `INSERT`, `UPDATE`, หรือ `UPSERT` กับตารางที่มี JSONB หรือ Text ก้อนใหญ่ (เช่น `kps_cloud_store`):
  - **ห้ามเด็ดขาด**: ห้ามใส่ `RETURNING *` เพราะฐานข้อมูลจะส่งก้อนข้อมูลขนาดใหญ่ที่เพิ่งเซฟย้อนกลับมาทาง Egress
  - ให้ใช้ `RETURNING "key", "updated_at"` หรือ `RETURNING "id"` เท่านั้น
  - หากต้องการยืนยันผลการบันทึก ให้ใช้สถานะ HTTP Status 200/204 หรือตรวจเฉพาะ Error Code

==================================================
4. 🧩 GRANULAR SCOPE & KEY SHARDING (ห้ามเก็บไข่ทุกฟองในตะกร้าเดียว)
==================================================
- **ห้ามเก็บข้อมูลทั้งโรงเรียนไว้ใน Key เดียว หรือ Row เดียว**:
  - หลีกเลี่ยง Monolithic Blobs เช่น การเก็บประวัติเช็คชื่อหรือเกรดของทั้งโรงเรียนไว้ใน Key `all_attendance`
  - ให้แยก Scope ย่อยตามมิติการทำงานจริง (Sharding):
    - ตามห้องเรียน: `cls_students_room-1-1`, `attendance:2569:1:room-101`
    - ตามวิชา: `grades:2569:1:subj_th101`
  - การบันทึกข้อมูลของห้อง ม.1/1 ต้องกระทบเฉพาะ Key ของห้องตนเอง และต้องไม่บีบให้ครูห้อง ม.4/1 ต้องดาวน์โหลดข้อมูลใหม่

==================================================
5. 💤 SCALE-TO-ZERO & COMPUTE CONSERVATION (ให้ฐานข้อมูลหลับได้จริง)
==================================================
- Neon Serverless จะปิดตัว (Scale to Zero) อัตโนมัติเมื่อไม่มี Connection นานเกิน 5 นาที เพื่อหยุดนับชั่วโมง Compute Hours
- **ข้อห้ามเพื่อป้องกันฐานข้อมูลตื่น 24 ชม.**:
  - ❌ ห้ามตั้งเวลาวนลูป Polling ถี่ๆ (`setInterval`) เช็คข้อมูลทุกๆ 10–30 วินาที
  - ❌ ห้ามเปิด `revalidateOnFocus` ถ้าข้อมูลไม่ได้ต้องการ Realtime วิกฤต
  - ให้ใช้ Event-driven หรือ Manual Refresh เมื่อผู้ใช้กดปุ่ม หรือ Debounce บันทึกข้อมูล (ขั้นต่ำ 1,200ms)
- **การเชื่อมต่อ**:
  - ต้องใช้ Connection String แบบ Pooler (`-pooler`) เสมอบน Vercel/Serverless Functions เพื่อให้ Connection ปิดตัวเร็วและไม่ค้างในระบบ

==================================================
6. 🖼️ R2-ONLY STORAGE FOR ALL ASSETS & DOCUMENTS (ไฟล์เอกสารทุกชนิดต้องเก็บใน CLOUDFLARE R2 เท่านั้น)
==================================================
- **กฎเหล็กการจัดเก็บไฟล์เอกสารและสื่อทุกประเภท: ต้องอัปโหลดลง Cloudflare R2 เท่านั้น**:
  - **ขอบเขตเอกสารที่ครอบคลุม**:
    - **ใบรับรองแพทย์ (Medical Certificates)** ของนักเรียนและบุคลากร
    - **เอกสารแนบการลา (Leave Attachments)** และหนังสือรับรอง
    - **เอกสารราชการและสแกน (Document Records, Scans, Inbound/Outbound Routing)**
    - **ไฟล์ภาระงาน/การบ้าน (Assignment Submissions & Work Attachments)**
    - **ใบเสร็จ/หลักฐานการเงิน (Budget & Expense Receipts)**
    - **ไฟล์ PDF, สแกนหลักฐาน, ภาพถ่าย และลายเซ็นดิจิทัลทั้งหมด**
  - **ข้อห้ามเด็ดขาด**:
    - ❌ ห้ามเก็บไฟล์รูปภาพ, เอกสารสแกน, ลายเซ็น, PDF เป็น Base64 หรือ Binary Blob ลงใน PostgreSQL / Neon DB โดยเด็ดขาด
    - ❌ ห้ามอัปโหลดเอกสารไปไว้ใน Local Server Storage หรือบริการอื่นที่มีค่า Data Egress สูง
  - **แนวทางปฏิบัติ**:
    - ในตารางฐานข้อมูล ให้เก็บเฉพาะ `storageKey` หรือ URL ภายนอกของ Cloudflare R2 เท่านั้น
    - Cloudflare R2 เป็นเป้าหมายหลักมาตรฐานของระบบเพราะไม่มีค่าบริการ Data Transfer/Egress (Zero Egress Fee) และเชื่อมต่อผ่าน S3-compatible API ได้อย่างรวดเร็ว
    - การเปิดดูไฟล์หรือดาวน์โหลด ให้ใช้ R2 Public Domain หรือ Signed URL ที่มีอายุตามกำหนด

==================================================
7. 🛡️ SCHEMA DRIFT & DROP PROTECTION (ลงทะเบียนตารางใน PRISMA ให้ครบ)
==================================================
- **ทุกตารางที่มีอยู่จริงในฐานข้อมูล ต้องมีโมเดลระบุไว้ใน `schema.prisma`**:
  - แม้จะเป็นตารางที่สร้างด้วย Raw SQL (เช่น `kps_cloud_store`) ก็ต้องนิยามโมเดลไว้
  - ป้องกันไม่ให้คำสั่ง `npx prisma db push` หรือ Migration ของทีมงานมองว่าเป็นตารางส่วนเกินแล้วเผลอสั่ง DROP TABLE
  - ตรวจสอบ Index และ Unique Constraints ใน `schema.prisma` ให้ตรงกับฐานข้อมูลจริงเสมอ
