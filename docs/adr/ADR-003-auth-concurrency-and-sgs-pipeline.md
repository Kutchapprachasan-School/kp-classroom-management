# ADR-003: สถาปัตยกรรมระบบยืนยันตัวตนแบบผสมผสาน (Hybrid Auth), การควบคุม Concurrency ด้วย Optimistic Versioning และไปป์ไลน์ส่งออก SGS/SAR แบบ Immutable Snapshot

## สถานะ (Status)
**APPROVED (อนุมัติจากการ Grill-Doc รอบที่ 2)**

## บริบท (Context)
จากการวิเคราะห์ระบบในรอบ Grill-Doc ที่ 2 ร่วมกับผู้ใช้งาน เพื่อเตรียมความพร้อมสำหรับ Production ระบบต้องการข้อตกลงเชิงสถาปัตยกรรมที่ชัดเจนใน 3 ประเด็นสำคัญ:
1. **การยืนยันตัวตน (Authentication):** บริบทโรงเรียนไทย ครูต้องการทั้ง Google OAuth (เพื่อซิงก์ Google Classroom) และ Email/Password แบบดั้งเดิม ส่วนนักเรียน ม.1 - ม.3 ร้อยละ 60 ไม่มีอีเมลหรือไม่จำรหัสผ่านยาวๆ
2. **การป้องกันคะแนนชนกัน (Concurrency Control):** ในช่วงปิดเทอม อาจมีครูประจำวิชาและครูช่วยสอนเปิดหน้าต่างแก้ไขคะแนนในชิ้นงานเดียวกันพร้อมกัน
3. **การส่งออกข้อมูล SGS และรายงาน SAR (SGS / SAR Export Pipeline):** ต้องรับประกันความถูกต้องตามโครงสร้าง สพฐ. 100% ป้องกันการแก้ไขไฟล์ภายนอก และมี Snapshot ย้อนหลังเพื่อรองรับการประเมิน วPA

---

## การตัดสินใจเชิงสถาปัตยกรรม (Architectural Decisions)

### 1. ระบบยืนยันตัวตนแบบผสมผสาน (Hybrid Authentication Provider)
- **ฝั่งคุณครู (Teachers & Administrators):**
  - รองรับ **Dual-Mode Login**: สามารถเลือกล็อกอินด้วย Google Workspace for Education (Google OAuth SSO) หรือใช้อีเมลโรงเรียน (`@school.ac.th`) ร่วมกับรหัสผ่านแบบดั้งเดิม (Supabase Auth Email/Password)
- **ฝั่งนักเรียน (Students):**
  - เข้าสู่ระบบด้วย **"รหัสนักเรียน 5 หลัก + PIN วันเกิด 4 หลัก"** (เช่น `45102` + `2510`) หรือการสแกน **QR Code ประจำตัว** ที่คุณครูพิมพ์แจกจากหน้าระบบ
  - ระบบสร้าง Session Token ที่ปลอดภัยแบบ Shadow Auth ใน Supabase เพื่อแยกบทบาท (RBAC) เป็น `STUDENT` และจำกัดการเข้าถึงเฉพาะข้อมูลห้องเรียนของตนเองเท่านั้น

### 2. การควบคุม Concurrency ด้วย Optimistic Locking (`version` Stamp)
- ตารางคะแนน (`Score`) และข้อมูลที่แก้ไขได้บ่อยทุกเรคอร์ด จะมีฟิลด์ `version` (จำนวนเต็มเริ่มต้นที่ 1 และเพิ่มขึ้นทุกครั้งที่มีการบันทึก)
- เมื่อครูส่งคำขออัปเดตคะแนน ระบบจะทำการตรวจสอบ:
  $$\text{WHERE id} = \text{scoreId} \quad \text{AND} \quad \text{version} = \text{expectedVersion}$$
- หากไม่ตรงกัน (เกิดจากมีผู้อื่นบันทึกคะแนนไปก่อนหน้า) ระบบจะไม่ยอมเขียนทับ (Silent Overwrite) แต่จะส่ง `ConflictError (HTTP 409)` แจ้งเตือนผู้ใช้ว่า *"มีผู้อื่นแก้ไขคะแนนนี้ไปก่อนหน้า กรุณารีเฟรชเพื่อตรวจสอบข้อมูลล่าสุด"*

### 3. ไปป์ไลน์ส่งออก SGS และ SAR แบบ Server-side Immutable Snapshot
- ก่อนการส่งออก ระบบจะรัน Invariant Checker ตรวจสอบว่า:
  1. คะแนนรวมทุกหน่วยการเรียนรู้และปลายภาคคำนวณไม่เกิน 100 คะแนน
  2. ไม่มีช่องคะแนนว่างที่ไม่ได้รับการยกเว้น (Exempt) หรือยังไม่ได้เติม 0
- เมื่อตรวจสอบผ่าน ระบบจะสร้างไฟล์ `.xlsx` ตามฟอร์แมต SGS สพฐ. และบันทึกเป็น **Immutable Snapshot** ลงใน Supabase Storage (`sgs-exports/{termId}/{classroomId}/`)
- สร้างเรคอร์ดใน `SgsExportLog` พร้อมค่าแฮช SHA-256, ผู้ส่งออก, วันเวลาที่ส่งออก เพื่อใช้เป็นหลักฐานยืนยันความถูกต้องในรายงาน SAR และการประเมิน วPA

## ผลลัพธ์และข้อดี (Consequences & Benefits)
- นักเรียนเข้าถึงระบบห้องเรียนผจญภัยได้ง่าย 100% ไม่มีปัญหาเด็กติดค้างเพราะลืมรหัสผ่าน
- ป้องกันปัญหาข้อมูลคะแนนสูญหายจากการบันทึกทับกัน (Race Condition / Lost Updates)
- ข้อมูลผลการเรียนที่ส่งออกเข้า SGS มีหลักฐานยืนยันความถูกต้อง ไม่สามารถถูกดัดแปลงนอกระบบได้
